# SwiftDeploy

A declarative container deployment CLI. Write a `manifest.yaml` that describes your entire stack. SwiftDeploy generates all config files from it, manages the container lifecycle, and keeps your service running.

The manifest is the single source of truth. Nothing is handwritten. The grader can delete generated files and run `swiftdeploy init` to regenerate them correctly.

## Project Structure

```
swiftdeploy-project/
  manifest.yaml             # Single source of truth — edit this only
  swiftdeploy               # CLI tool (executable Python script)
  app/
    main.py                 # FastAPI service (stable + canary modes)
    requirements.txt
    Dockerfile
  templates/
    nginx.conf.j2           # Jinja2 template for Nginx config
    docker-compose.yml.j2   # Jinja2 template for Docker Compose
  nginx.conf                # Generated by swiftdeploy init
  docker-compose.yml        # Generated by swiftdeploy init
  README.md
```

- Ubuntu 22.04 or 24.04 VPS (minimum 2 vCPU, 2GB RAM)

## Setup from Scratch

### Step 1: Install Docker

```bash
curl -fsSL https://get.docker.com | sh
sudo usermod -aG docker $USER
newgrp docker
docker --version
```

### Step 2: Clone the repository

```bash
git clone https://github.com/GideonBature/hng-stage4.git
cd hng-stage4
```

### Step 3: Install CLI dependencies

```bash
pip3 install pyyaml jinja2 requests
```

### Step 4: Make the CLI executable

```bash
chmod +x swiftdeploy
```

### Step 5: Deploy the full stack

```bash
./swiftdeploy deploy
```

This runs `init` to generate configs, builds the Docker image, brings up the stack, and waits for health checks to pass.

### Step 6: Verify the service is running

```bash
curl http://localhost:8080/
curl http://localhost:8080/healthz
```

## Subcommand Walkthrough

### `init`

Parses `manifest.yaml` and generates `nginx.conf` and `docker-compose.yml` from Jinja2 templates. These files are the only outputs. Everything else in the stack derives from the manifest.

```bash
./swiftdeploy init
```

Expected output:

```
Running init...
  Generated nginx.conf
  Generated docker-compose.yml
Init complete.
```

### `validate`

Runs 5 pre-flight checks before deployment. Exits non-zero if any check fails.

```bash
./swiftdeploy validate
```

The five checks are:

1. `manifest.yaml` exists and is valid YAML
2. All required fields are present and non-empty
3. The Docker image referenced in the manifest exists locally
4. The Nginx port is not already bound by another process
5. The generated `nginx.conf` is syntactically valid

Expected output:

```
Running validate...
  [PASS] manifest.yaml exists and is valid YAML
  [PASS] All required manifest fields present and non-empty
  [PASS] Docker image 'swift-deploy-1-node:latest' exists locally
  [PASS] Nginx port 8080 is available
  [PASS] nginx.conf is syntactically valid

Validation complete: 5 passed, 0 failed
```

### `deploy`

Runs `init`, builds the Docker image, brings up the full stack, and blocks until health checks pass or 60 seconds elapse.

```bash
./swiftdeploy deploy
```

Expected output:

```
Running deploy...
Running init...
  Generated nginx.conf
  Generated docker-compose.yml
Init complete.
Building image swift-deploy-1-node:latest...
Image built successfully.
Starting stack...
Waiting for health checks on port 8080...
Stack is healthy. Service available at http://localhost:8080
```

### `promote`

Switches the deployment mode between `stable` and `canary` with a rolling restart of the service container only. Nginx is never restarted.

```bash
# Switch to canary
./swiftdeploy promote canary

# Switch back to stable
./swiftdeploy promote stable
```

What happens internally:

1. Updates the `mode` field in `manifest.yaml`
2. Regenerates `docker-compose.yml` with the new `MODE` environment variable
3. Restarts the service container only using `--force-recreate --no-deps`
4. Waits for the health check to confirm the new mode is active
5. Hits `/healthz` and prints the confirmed mode
6. If health check fails, automatically rolls back to the previous mode

Expected output for `promote canary`:

```
Promoting to canary mode...
  Updated manifest.yaml: mode = canary
  Regenerated docker-compose.yml
  Restarting swiftdeploy-app container...
  Waiting for health check...
Promotion successful. Service is running in canary mode.
  /healthz response: {'status': 'ok', 'mode': 'canary', 'version': '1.0.0', 'uptime_seconds': 0}
```

In canary mode, every response includes `x-mode: canary` header and the `/chaos` endpoint becomes active.

### `teardown`

Removes all containers, networks, and volumes.

```bash
./swiftdeploy teardown

# Also delete generated config files
./swiftdeploy teardown --clean
```

## The Manifest

`manifest.yaml` is the only file you edit. Everything else is generated from it.

```yaml
services:
  image: swift-deploy-1-node:latest
  port: 3000
  mode: stable
  version: "1.0.0"
  replicas: 1
  restart_policy: unless-stopped
  log_volume: app-logs

nginx:
  image: nginx:latest
  port: 8080
  proxy_timeout: 30

network:
  name: swiftdeploy-net
  driver_type: bridge
```

## The API Service

The service runs in `stable` or `canary` mode, controlled by the `MODE` environment variable injected at container startup from the manifest.

| Endpoint | Method | Description |
|----------|--------|-------------|
| `/` | GET | Welcome message with current mode, version, and server timestamp |
| `/healthz` | GET | Liveness check returning status and process uptime in seconds |
| `/chaos` | POST | Simulate degraded behaviour (canary mode only) |

**Canary mode** adds `x-mode: canary` to every response and activates the chaos endpoint.

### Chaos endpoint

```bash
# Slow all responses by N seconds
curl -X POST http://localhost:8080/chaos \
  -H "Content-Type: application/json" \
  -d '{"mode": "slow", "duration": 3}'

# Return 500 on ~50% of requests
curl -X POST http://localhost:8080/chaos \
  -H "Content-Type: application/json" \
  -d '{"mode": "error", "rate": 0.5}'

# Cancel all chaos
curl -X POST http://localhost:8080/chaos \
  -H "Content-Type: application/json" \
  -d '{"mode": "recover"}'
```

## Nginx Behaviour

- Listens on `nginx.port` (default 8080)
- Proxy timeouts set from `nginx.proxy_timeout`
- Returns JSON error bodies on 502, 503, and 504
- Adds `X-Deployed-By: swiftdeploy` header to all responses
- Forwards `X-Mode` header from the upstream service
- Access logs in format: `$time_iso8601 | $status | $request_time s | $upstream_addr | $request`
- Service port (3000) is never exposed directly, all traffic routes through Nginx

---

## Docker and Security

- Service container runs as a non-root user (`appuser`)
- All Linux capabilities are dropped except `NET_BIND_SERVICE`
- Image is under 300MB (uses `python:3.11-alpine` with multi-stage build)
- `MODE`, `APP_VERSION`, and `APP_PORT` are injected from the manifest
- Health check uses Python's `urllib.request` (no external tools needed)
- Service port is never published to the host, only Nginx port is exposed
