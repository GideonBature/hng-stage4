# SwiftDeploy

A declarative container deployment CLI. Write a `manifest.yaml` that describes your entire stack. SwiftDeploy generates all config files from it, manages the container lifecycle, and keeps your service running.

The manifest is the single source of truth. Nothing is handwritten. The grader can delete generated files and run `swiftdeploy init` to regenerate them correctly.

## Project Structure

```
swiftdeploy-project/
  manifest.yaml          # Single source of truth — edit this only
  swiftdeploy            # CLI tool (executable Python script)
  app/
    main.py              # FastAPI service (stable + canary modes)
    requirements.txt
    Dockerfile
  templates/
    nginx.conf.j2        # Jinja2 template for Nginx config
    docker-compose.yml.j2
  nginx.conf             # Generated by swiftdeploy init
  docker-compose.yml     # Generated by swiftdeploy init
  README.md
```

## Setup from Scratch

### Step 1: Clone the repository

```bash
git clone https://github.com/GideonBature/hng-stage4.git
cd hng-stage4
```

### Step 2: Install CLI dependencies

```bash
pip install pyyaml jinja2 requests
```

### Step 3: Make the CLI executable

```bash
chmod +x swiftdeploy
```

### Step 4: Generate configs from the manifest

```bash
./swiftdeploy init
```

This reads `manifest.yaml` and generates `nginx.conf` and `docker-compose.yml`.

### Step 5: Validate before deploying

```bash
./swiftdeploy validate
```

### Step 6: Deploy the full stack

```bash
./swiftdeploy deploy
```

This builds the Docker image, brings up the stack, and waits for health checks to pass.

### Step 7: Test the service

```bash
curl http://localhost:8080/
curl http://localhost:8080/healthz
```

## Subcommand Walkthrough

### `init`

Parses `manifest.yaml` and generates all config files from Jinja2 templates.

```bash
./swiftdeploy init
```

Output:
```
Running init...
  Generated nginx.conf
  Generated docker-compose.yml
Init complete.
```

### `validate`

Runs 5 pre-flight checks and exits non-zero on any failure.

```bash
./swiftdeploy validate
```

Checks:
1. `manifest.yaml` exists and is valid YAML
2. All required fields are present and non-empty
3. Docker image referenced in manifest exists locally
4. Nginx port is not already bound on the host
5. Generated `nginx.conf` is syntactically valid

Output:
```
Running validate...
  [PASS] manifest.yaml exists and is valid YAML
  [PASS] All required manifest fields present and non-empty
  [PASS] Docker image 'swift-deploy-1-node:latest' exists locally
  [PASS] Nginx port 8080 is available
  [PASS] nginx.conf is syntactically valid

Validation complete: 5 passed, 0 failed
```

### `deploy`

Runs `init`, builds the image, brings up the stack, and blocks until health checks pass or 60 seconds elapse.

```bash
./swiftdeploy deploy
```

### `promote`

Switches between stable and canary mode with a rolling service restart.

```bash
# Switch to canary
./swiftdeploy promote canary

# Switch back to stable
./swiftdeploy promote stable
```

What it does:
1. Updates the `mode` field in `manifest.yaml`
2. Regenerates `docker-compose.yml` with the new `MODE` env var
3. Restarts the service container only (Nginx is not touched)
4. Confirms the new mode via `/healthz`
5. If health check fails, automatically rolls back

### `teardown`

Removes all containers, networks, and volumes.

```bash
./swiftdeploy teardown

# Also delete generated configs
./swiftdeploy teardown --clean
```

## The API Service

The service runs in stable or canary mode controlled by the `MODE` environment variable.

| Endpoint | Method | Description |
|----------|--------|-------------|
| `/` | GET | Welcome message with mode, version, timestamp |
| `/healthz` | GET | Liveness check with uptime in seconds |
| `/chaos` | POST | Simulate degraded behaviour (canary only) |

Canary mode adds `X-Mode: canary` to every response and activates the chaos endpoint.

### Chaos endpoint examples

```bash
# Slow responses for N seconds
curl -X POST http://localhost:8080/chaos \
  -H "Content-Type: application/json" \
  -d '{"mode": "slow", "duration": 3}'

# Return 500 on ~50% of requests
curl -X POST http://localhost:8080/chaos \
  -H "Content-Type: application/json" \
  -d '{"mode": "error", "rate": 0.5}'

# Cancel chaos
curl -X POST http://localhost:8080/chaos \
  -H "Content-Type: application/json" \
  -d '{"mode": "recover"}'
```

## The Manifest

`manifest.yaml` is the only file you edit. Everything else is generated from it.

```yaml
services:
  image: swift-deploy-1-node:latest
  port: 3000
  mode: stable
  version: "1.0.0"
  replicas: 1
  restart_policy: unless-stopped
  log_volume: app-logs

nginx:
  image: nginx:latest
  port: 8080
  proxy_timeout: 30

network:
  name: swiftdeploy-net
  driver_type: bridge
```

---

## Nginx Behaviour

- Listens on `nginx.port` (default 8080)
- Proxy timeouts configured from `nginx.proxy_timeout`
- Returns JSON error bodies on 502/503/504
- Adds `X-Deployed-By: swiftdeploy` header to all responses
- Forwards `X-Mode` header from upstream
- Access logs in format: `$time_iso8601 | $status | ${request_time}s | $upstream_addr | $request`
